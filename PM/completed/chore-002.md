## Human-in-the-middle protocol

- Work through the gates in order; a checklist is not permission to execute.
- At each gate, inspect the present state read-only, summarize the proposed
  single action and its effect, then ask the owner with the interactive question
  tool. Wait for that specific answer before any external mutation.
- Ask one question at a time. Use proceed, defer, or stop choices. Approval of
  this checklist, or of a previous gate, does not authorize later actions.
- Never request a token value in chat, logs, or a tracked file. The owner enters
  secrets through GitHub's secure UI or a secure interactive CLI prompt.
- When a publish script asks for input, relay the exact decision to the owner
  interactively. Do not automate `Read-Host`, simulate approval, or feed canned
  answers for real deployments.
- Use no more than two bounded verification attempts per gate. Stop on a
  cancellation, repeated failure, conflict, or unexpected target; record the
  evidence and ask for direction instead of expanding scope.
- Check a box only after its stated result is observed. Record timestamp,
  non-secret evidence (run URL, hostname, branch/SHA), and the owner's decision.
  A configured setting is not proof of a successful deployment.
- Keep this item in `current/` until the owner explicitly confirms all acceptance
  criteria. Split PM housekeeping from code changes per the branching policy;
  obtain approval before committing, switching, merging, or pushing.
