# Solitaire

Static vanilla JavaScript browser/PWA starter, bootstrapped with the Ignyos
Project Toolkit Full Profile in Greenfield mode. **Gameplay is not implemented.**
There is no compilation or package installation step. See [PM](PM/project-management.md)
for work status and [AGENTS.md](AGENTS.md) for agent direction.

## Local development

Requires PowerShell 7 (`pwsh`) and Git. VS Code's PowerShell extension enables the
Run & Debug entries. Python 3 is used only by the optional local server task.

```powershell
.\build.ps1
python -m http.server 4173 --bind 127.0.0.1 --directory .\docs
```

Open http://127.0.0.1:4173/. HTTPS or localhost is required for offline support.
The scaffold is deployment-relative and supports Pages subdirectory previews.
Use the VS Code **Build** and **Serve** tasks or the **Build**, **Publish-dev**,
and **Publish-live** Run & Debug configurations. Publishing entries commit/push:
do not run them just to preview the page.

`clean.ps1` is intentionally non-destructive: `docs/` is the application source,
not disposable output. Release audits and PM records are not build outputs.

## Deployment targets and external prerequisites

[deploy-config.psd1](deploy-config.psd1) is the target source of truth:

| Lane | Source | Pages host | Pages repository |
|---|---|---|---|
| Production | `main`, `docs/` | solitaire.ignyos.com | Ignyos/solitaire |
| Dev | `dev`, staging copy of `docs/` | solitaire-dev.ignyos.com | Ignyos/solitaire-dev |

Before deploying, the owner must:

1. Create/configure the external `Ignyos/solitaire-dev` repository with Pages
   publishing from `main` / repository root. The action replaces that branch
   with an orphan deployment snapshot; do not store development source there.
2. Set source-repository Actions secrets `DEV_PAGES_REPO=Ignyos/solitaire-dev` and
   `DEV_PAGES_TOKEN` (a token restricted to writing the external dev repository).
   Never store the token in tracked files.
3. Enable source-repository Pages from `main` / `docs`, not from `dev`.
4. Configure both custom domains and DNS independently, verify ownership as
   applicable, and enable HTTPS. The bootstrap does not provision these resources.
5. Review branch protection, token permissions, and action availability before publishing.

The dev workflow rejects non-dev dispatches and mismatched/same-repository
targets. It overrides CNAME only in `.pages-dev/`; the tracked `docs/CNAME`
always remains production-only. Non-production hosted pages show **DEVELOPER
PREVIEW**; localhost, loopback, file previews, and the exact production hostname do not.

## Dev publishing

Merge confirmed implementation branches into `dev` using the review policy chosen
by the developer. Start with a clean tree. Run `.\dev-publish.ps1`.
After validation, the script asks once: `You are about to publish to dev. Continue?
[Y]es/[N]o (default No)`. Enter `Y`/`Yes` to authorize publishing, or `N`/`No`
or press Enter to cancel. Input is case-insensitive and ignores surrounding
whitespace; invalid input also cancels without changes. This confirmation
authorizes the deployment only: the script does not request per-item evidence or
move, edit, or promote/demote candidates. Every `release-candidate-dev/` item
stays there after a successful publish; any lifecycle transition is a separate
PM change. After confirmation, the script stamps assets/cache, validates,
commits, and pushes only `dev`.

`-WhatIfMode` is read-only and still enforces the dev branch gate; it does not
prompt. The publish confirmation is not evidence that the push or deployment
succeeded, nor verification of any candidate item.
`-NoPush` creates a local commit but does not deploy.
Repeated publishes in the same UTC minute are rejected, even for PM-only changes,
so every real publish gets a fresh cache identity.

## Production release

On clean `main`, run `.\release.ps1`. One UTC `yyyy-MM-dd-HH-mm` stamp identifies
HTML assets, the service worker cache, release diff filename, and annotated tag.
The script rejects duplicate timestamps, requires explicit preparation approval,
retires the previous `completed/` items in a separate commit, then moves all
production candidates to `completed/`, stamps assets, and saves the diff audit.
Prepared application and PM changes are staged before generating the audit so
newly moved item paths are included.

The audit compares the previous reachable timestamp release tag (or the empty
tree for the first release) against the prepared tree, including version and PM
changes. Notes and historical audit files are excluded to prevent recursive diffs.
The emitted AI directive grounds notes in that evidence and the
[style guide](RELEASE_NOTES_STYLE.md); the script copies it to the clipboard for
pasting into the AI prompt. If clipboard access fails, the directive is printed
for manual copying. Update notes in another terminal/editor while the script
waits, then enter `R` to release or `C` to cancel; the choice is
case-insensitive.

If code or HEAD changes during the notes gate, the script aborts rather than
tagging unreviewed contents. Approved notes/audit are committed, a bare timestamp
tag is created, and branch/tag are pushed atomically. The tag workflow validates
the production ancestry, cache identity, audit, and notes before publishing a
GitHub Release with the notes body and audit attachment.

On non-main branches, or with `-WhatIfMode`, release is a read-only rehearsal:
no files, PM moves, commits, tags, prompts, or pushes. `-NoPush` on main still
creates local commits and a tag. Cancellation after preparation leaves changes
for review; the previous-completed cleanup commit may already exist. Do not
blindly rerun against a dirty tree or discard prepared changes.
